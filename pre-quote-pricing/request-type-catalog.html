Pre-Quote Pricing — Request-Type & Field CatalogStraw man · react & correct

A first-principles draft of the pricing changes that happen before a quote goes out: the request types, the fields each one needs, how it should route, and where it breaks today. Built to be argued with — the point of the scoping call is to break and extend it, not approve it.

How to read this.

These six types were drafted from first principles plus the one worked example (Felipe's) — not reconstructed from the ticket log, because the ticket log doesn't hold this data reliably. That absence is the headline finding, not a gap in this doc: the future system exists precisely because today's requests live in email, Teams, and spreadsheets with no record of who asked or who approved. So the call's job is to confirm the list is complete, split correctly, and has the right required fields. Fields marked * are proposed as required.

Common fields — every request carries these

Proposed shared header, so any request is recorded, routable, and auditable regardless of type.

Requester + team Request type Opportunity / quote / deal reference Customer / account + region Business justification Needed-by date Urgent? + blocked artifact (quote / order / invoice) Product(s) / part number(s), or "new"

The six request types

Each maps to a routing default — fast track (straightforward, straight to execution), full review (new commercial design), or threshold (routing depends on the amount, tied to delegated authority). These defaults mirror the product-licensing intake so the two systems behave consistently.
01

New-product pricing

Full review
Setting the price for a product or offering that isn't in the price book yet, so it can be quoted.
Type-specific fields
Offering / product namePricing model (subscription / consumption / perpetual / …) List price + currencyCharge type Comparable existing product (benchmark)GA / launch date
Where it breaks today

Price is decided in a spreadsheet and never recorded against a part; the launch waits on it; no benchmark trail.

Ask Kevin  Does this overlap with the product-licensing "create part number" flow, or is pre-quote pricing decided before the part exists — i.e. is this the same request seen from two sides?
02

Pre-quote discount / exception approval

Threshold
A discount beyond standard, or a non-standard term, needed to quote a specific deal.
Type-specific fields
Standard priceRequested price (→ discount %) Reason / competitive contextDeal size + term Approver tier neededApproval expiry date
Where it breaks today

Approval is a one-line email, with no threshold logic, no expiry, and no record — the single-point bottleneck.

Ask Kevin  What are the current discount thresholds and who approves each tier? (This is what turns routing from a guess into a rule.)
03

Region or currency setup

Fast / review
Enabling an existing product to be sold in a new region or currency.
Type-specific fields
Product / partTarget region(s) Target currency(ies)Price basis (FX convert vs locally set) Effective dateTax / legal-entity notes
Where it breaks today

Done ad hoc with inconsistent FX; no policy applied; nothing recorded, so the next region starts from scratch.

Ask Kevin  Is there an approved FX / localization policy? If yes, straight conversion is fast-track; if each case is bespoke, it's review.
04

Bundle or packaging change

Full review
Combining or splitting products into a sellable bundle, or changing what's inside one.
Type-specific fields
Bundle nameComponent parts + quantities Bundle price vs sum-of-parts (→ implied discount)Replaces / deprecates which parts Effective date
Where it breaks today

Bundles get assembled inside individual quotes ad hoc; there's no canonical bundle definition to reuse or audit.

Ask Kevin  Are bundles a real catalog object today, or assembled per quote every time?
05

Custom / customer-specific part creation

Fast + dedupe
A one-off or customer-specific part needed to quote a particular deal.
Type-specific fields
Base / parent partWhat's customized CustomerOne-time vs reusable PriceWhy an existing part won't serve (dedupe)
Where it breaks today

Custom parts proliferate with no dedupe and no reuse — the root of catalog sprawl on the licensing side too.

Ask Kevin  What share of "custom" parts are actually reusable? That number is the sprawl driver and the case for a dedupe gate.
06

Promotional pricing

Review + expiry
A time-boxed promotion or discount on a product or set of products.
Type-specific fields
Promo nameProducts in scope Promo price or % offStart + end date Eligibility (region / segment / deal size)Stackable with other discounts?
Where it breaks today

Promos linger past their expiry; there's no central record and no clean way to audit the revenue impact.

Ask Kevin  Who owns promo sign-off, and how should expiry be enforced so a promo can't outlive its end date?

Shared mechanics (inherited from the intake design)

Two-step approval: commercial sign-off → operations accept Timestamped audit trail on every request "No part number / no price, no quote" guardrail Deal-desk exception path Urgent = the blocked artifact is a required field

Assumptions to confirm on the call

  • These six types are complete — nothing common is missing — and non-overlapping. Most likely correction: whether "new-product pricing" and "custom part creation" collapse into, or split from, the licensing-side "create part number".
  • Discount / exception routing is threshold-based, which assumes delegated pricing authority exists or is being defined. If it isn't yet, everything escalates until it is.
  • Pre-quote pricing is a sibling to product-licensing intake, sharing the chassis (routing, approval, audit) but its own request types. Confirm they aren't actually one system.
  • The required-field marks (*) are a proposal; the practitioner questionnaire and the forwarded email threads will correct them.
  • Once validated, this becomes a live clay-model straw man like the intake prototype — reactable, not just readable.
